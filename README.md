# طبقة المحادثة الذكية — منصة السياحة الذكية في سوريا

خدمة Python (FastAPI) تمثل طبقة المحادثة لمنصة سياحية: تفهم رسائل المستخدم
(عربي/إنكليزي/عامية سورية/مختلط)، تدير الحوار وتتابع السياق، وتستدعي محركي
التوصية والتخطيط (حاليًا نسخ وهمية `app/mocks/` ملتزمة بـ `docs/contract.md`).

راجع `CLAUDE.md` للقواعد الصارمة، و`docs/spec.md` للمواصفات الكاملة،
و`docs/contract.md` لعقد البيانات مع المحركين، و`docs/plan.md` لخطة البناء.

## التشغيل

```bash
python3.12 -m venv venv
source venv/bin/activate          # أو venv\Scripts\activate على ويندوز
pip install -r requirements.txt

uvicorn app.main:app --host 127.0.0.1 --port 8001 --reload
```

`GET /health` للتأكد من عمل الخدمة. `POST /chat` يتطلب رأس
`X-Internal-Secret` (القيمة الافتراضية للتطوير: `dev-secret-change-me`،
يُضبط عبر متغير البيئة `INTERNAL_SECRET` — راجع `app/config.py`).

مثال استدعاء:

```bash
curl -X POST http://127.0.0.1:8001/chat \
  -H "Content-Type: application/json" \
  -H "X-Internal-Secret: dev-secret-change-me" \
  -d '{"session_id": "s1", "user_id": "u1", "message": "اقترحلي أماكن تاريخية بدمشق"}'
```

### Redis

الجلسات تُخزَّن بـ Redis (`REDIS_URL`، افتراضيًا `redis://localhost:6379/0`).
إن تعذّر الاتصال بخادم Redis فعلي، تسقط الخدمة تلقائيًا لنسخة بديلة بالذاكرة
(`InMemoryRedis` في `app/conversation/session.py`) — مناسب للتطوير والاختبار
فقط، وليس للإنتاج (الجلسات تُفقد عند إعادة التشغيل).

## واجهة اختبار احترافية (web/test-client.html)

صفحة HTML/CSS/JS مستقلة بلا أي اعتماديات بناء أو مكتبات خارجية — تُفتح مباشرة
بالمتصفح (نقر مزدوج على الملف أو من قائمة "افتح باستخدام"):

```
web/test-client.html
```

المزايا:
- شريط جانبي لضبط عنوان الخدمة (Base URL) وX-Internal-Secret وUser ID
  وSession ID (يُحفظ محليًا بالمتصفح عبر localStorage)، مع مؤشر حي لحالة
  الاتصال (`/health`).
- 12 سيناريو جاهز بضغطة واحدة يغطي النوايا التسع كلها (بحث، تفاصيل بإشارة
  ترتيبية، إضافة بضمير، بناء خطة، تعديل جراحي، مقارنة، رفض، ترحيب، خارج
  النطاق) بالعربي والإنكليزي — مفيد لتجربة الكسر اليدوية بـ `docs/plan.md`.
- عرض غني للرد المنظم: بطاقات الأماكن (تقييم، وسوم، سبب التوصية)، الخطة كخط
  زمني يومي مع التكاليف والتنازلات (tradeoffs)، وجدول مقارنة بمحاوره الخمسة
  مع تمييز الخيار الأفضل.
- لوحتا تصحيح قابلتان للطي: الحالة (`state`) الحالية والرد الخام (JSON)
  الكامل من كل استدعاء — مفيدتان لتتبّع ذاكرة العمل وحالة الجلسة.

**تشغيل CORS:** الخدمة تسمح افتراضيًا بأي أصل (`CORS_ALLOW_ORIGINS=*`) كي
تعمل الصفحة سواء فُتحت من `file://` أو من خادم تطوير محلي. قيّد القيمة
بالإنتاج عبر متغير البيئة `CORS_ALLOW_ORIGINS` (قائمة مفصولة بفواصل).

## إعادة تدريب مصنّف النية

النموذج يتدرب تلقائيًا بالذاكرة عند أول استخدام إن لم يجد ملفًا محفوظًا (لا
حاجة لخطوة يدوية لتشغيل الخدمة أو الاختبارات لأول مرة). لإعادة التدريب صراحةً
وحفظ النموذج على القرص (بعد تعديل بيانات التدريب مثلًا):

```bash
python -m app.conversation.intent --train
```

يقرأ `data/seed_intents.txt` (صيغة كل سطر: `النص ||| النية`) ويحفظ الناتج في
`data/intent_model.pkl` (لا يُرفع لـ git).

## كيف تضيف...

### نية جديدة

**ممنوع** بدون موافقة صريحة (CLAUDE.md: 9 نوايا مغلقة). إن تمت الموافقة:
1. أضِف النية لقائمة `INTENTS` في `app/conversation/intent.py`.
2. أضِف 40-60 مثال تدريب متنوع (فصيح/عامي/إنكليزي/مختلط) في `data/seed_intents.txt`.
3. أضِف فرعًا لها في `app/conversation/dialogue.py` (`handle_turn`) وفق دليل
   قرار الاستدعاء بـ `docs/spec.md §4`.
4. أضِف قوالب ردودها ثنائية اللغة في `app/conversation/responses.py`.
5. أعد التدريب (`--train`) وشغّل `pytest -x -q`.

### مدينة جديدة

أضِف مفتاحًا بقاموس `CITIES` في `app/conversation/entities.py` (الاسم الرسمي
+ الأسماء الشعبية/الإنكليزية)، وأضِف أماكن تلك المدينة في `app/mocks/data.py`
إن أردت أن تظهر بنتائج البحث.

### قالب رد جديد أو تعديل نص موجود

كل النصوص المعروضة للمستخدم في `app/conversation/responses.py` فقط (قاموس
`T`) — لا تكتب نصوصًا مباشرة في `dialogue.py` أبدًا (قاعدة صارمة بـ CLAUDE.md).
أضِف صيغة أو صيغتين إضافيتين لكل مفتاح موجود لتنويع الردود.

### وسم اهتمام جديد

**ممنوع** بدون تعديل `docs/contract.md` أولًا (القاموس مغلق: راجع `TAG_VOCAB`
في `app/shared/models.py`). بعد التعديل: أضِف الكلمات المفتاحية بقاموس
`INTEREST_TAGS` في `app/conversation/entities.py`.

## أين يُستبدل كل mock لاحقًا (بدون تغيير طبقة المحادثة)

| الملف الوهمي | يُستبدل بـ | يستخدمه في dialogue.py |
|---|---|---|
| `app/mocks/recommender.py` (search/details/compare/log/profile) | محرك التوصية الحقيقي | `_handle_search`، `_handle_details`، `_handle_compare`، `_handle_add_to_plan`، `_handle_reject`، `_handle_greeting` |
| `app/mocks/planner.py` (build/modify/feasibility) | محرك التخطيط الحقيقي | `_handle_build_plan`، `_handle_modify_plan` |
| `app/mocks/data.py` | قاعدة بيانات الأماكن الحقيقية | يُستخدم داخل الملفين أعلاه فقط |

طالما الاستبدال يحافظ على نفس تواقيع الدوال (نفس الوسائط، ونفس بنية الإرجاع
حسب `docs/contract.md`)، **لا حاجة لتعديل أي سطر في `app/conversation/`.**

## بنية المشروع

راجع القسم "البنية الملزمة للمشروع" في `CLAUDE.md`. ملخص خط المعالجة
(`docs/plan.md` المخطط 1):

```
رسالة المستخدم
  → normalizer (تطبيع + كشف لغة)
  → resolver (حل الإشارات — قبل النية!)
  → intent (تصنيف النية، مع علامة __مكان_مشار_اليه__ إن وُجدت إشارة)
  → entities (استخراج الكيانات → تحديث الحالة)
  → dialogue (القرار + استدعاء الأداة المناسبة)
  → responses (تحديث ذاكرة العمل الإلزامي + الرد المنظم)
```

## قيود معروفة (نسخة أولى — mock)

- محلّل الإشارات يعمل فقط على الأماكن التي **ظهرت فعلًا** بالمحادثة (آخر
  مقترحات أو أماكن الخطة الحالية)، وليس على كامل قاعدة البيانات — سؤال مباشر
  عن مكان لم يُذكر بعد («Is Palmyra worth visiting?») يُعامَل كسؤال بلا سياق
  ويُطلب توضيح، إلى أن تُضاف قدرة استخراج أسماء أماكن صريحة لمستخرج الكيانات.
- `modify_plan` من نوع `shift_time` يعدّل توقيت المحطة المستهدفة دون إعادة
  حساب تتالي بقية محطات نفس اليوم تلقائيًا — كافٍ للنسخة الوهمية، يحتاج
  مراجعة عند ربط محرك تخطيط حقيقي.
- بيانات الأماكن ثابتة (18 مكانًا) بـ `app/mocks/data.py` — تُستبدل بقاعدة
  بيانات حقيقية دون تغيير عقد الحقول.
